Governance for Checkmarx One AI credits

Budget, watch, and cap AI credit spend — safely.

Checkmarx One spends AI credits on Triage, Remediation, DAST correlation, Fusion scans and Auto Triage, but gives you no way to budget them per user, group, project or application. CxCreditGuard polls consumption on a schedule, compares it against limits you define, and can restrict access when a budget is breached — with every restriction recorded and reversible in one click.

This guide walks an administrator from first deploy to running enforcement in production. If you only read one thing, read How usage is measured — it explains the single non-obvious idea the whole tool is built on.

01 — Start here

What CxCreditGuard is

It is a self-hosted governance layer that sits beside Checkmarx One. It never spends credits itself; it observes what Checkmarx reports and, when you ask it to, turns off the AI features that spend them. Three ideas shape everything:

Poll, don't stream

Checkmarx reports running totals over a lookback window, not individual events — so per-period usage is derived by comparison, not by summing events.

Attribute, don't guess

Every usage row is matched to a real user — exactly where possible, by similarity where not — and anything uncertain is surfaced for review instead of billed to the wrong person.

Act reversibly

Before any restriction, the prior state is snapshotted. Every enforcement is one click to undo, and a feature that was already off stays off on restore.

◆
Monitor first.

Every new limit defaults to monitor-only. Nothing is ever restricted until you deliberately switch a limit to enforce — so you can watch the numbers for a full budget period before anything acts.

02 — Start here

How it works

CxCreditGuard is one deployable unit: a backend that also serves the web UI from the same origin, a background scheduler in the same process, and a database (SQLite by default, PostgreSQL for the hardened deployment). Everything of consequence happens in one loop — a cycle — run on a schedule or on demand.

🔄 Sync
org_sync
Users, groups, projects, applications
→
📥 Ingest
ingestion
Poll consumption, snapshot, attribute to users
→
⚖️ Evaluate
evaluation
Usage vs limits, using period baselines
→
🛡️ Enforce
enforcement
Reversible role & AI-feature changes
Each step writes to the database and raises notifications; the web UI and email/webhook read from there.

You can run a cycle by hand any time from the Dashboard or Settings (Run a cycle now), which is the fastest way to see a change take effect without waiting for the schedule.

03 — Start here

Deploy

Two supported paths, both on Podman. Start with the single container to try it; use Compose to run it for real.

Quick start — single container

The whole tool ships in one image (UI bundled with the API) over plain HTTP on port 8000, with no required configuration: on first start it generates its own encryption key and a first admin account. From the repository root: 

# Linux / macOS / WSL
make podman-run

# Windows: run.bat (cmd.exe)  or  .\run-podman.ps1 (PowerShell)

Each builds the image, starts the container, and tails the startup log — which prints the initial admin credentials on a fresh volume. Then open http://localhost:8000.

▲
This convenience image runs over plain HTTP

Secure cookies are disabled because a browser silently discards them over HTTP. It is perfect for a local look, but do not expose it directly to the internet — use the Compose path for that.

Hardened deployment — Podman Compose

For production (HTTPS via an nginx TLS proxy, plus PostgreSQL), run the root docker-compose.yml with Podman Compose (Podman 4.1+):

cp .env.example .env
# Generate a master key for the .env file:
python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"

Set CXCG_MASTER_KEY (the value printed above — everything encrypted at rest depends on it) and POSTGRES_PASSWORD. To create the first admin, also set CXCG_BOOTSTRAP_ADMIN_USERNAME and CXCG_BOOTSTRAP_ADMIN_PASSWORD before the first start, then remove them after logging in. Provide a TLS certificate per deploy/nginx/README.md, then: 

podman compose -f docker-compose.yml up -d
podman compose -f docker-compose.yml logs -f app
⚠
Back up the data volume

The master key lives in cxcreditguard-data (single container) or your database plus CXCG_MASTER_KEY (Compose). Lose the key and stored Checkmarx secrets become unrecoverable.

04 — Start here

First-time setup

  1. Sign in and change the password. Use the credentials from the startup log (single container) or the ones you set in .env (Compose). You will be asked to change the password on first login.
  2. Connect Checkmarx. On the Setup page, paste an API key. The tool derives the tenant and region and shows them for you to confirm before anything is stored, then tests the connection. You can override the regional base URL if needed.
  3. Let a cycle run. Either wait for the schedule or press Run a cycle now. The first cycle syncs your organisation model and takes the first usage snapshot.
  4. Review attribution. Open Settings → Consumption attribution and clear any disputes so usage counts against the right people (see Attribution).
  5. Add limits in monitor mode and watch for a full period before enforcing (see Runbooks).
◆
Use a dedicated service account

Not a person's key. A named engineer's key inherits their permissions, breaks when they leave, and makes the audit trail read as though they personally restricted every colleague. A read-only key runs the whole tool in monitor-only mode.

05 — Daily use

The dashboard

The dashboard answers "what is being spent, by whom, and is anything at risk" at a glance.

  • Status tiles — credits reported for the window, entities near a limit, entities restricted, and the next scheduled run.
  • Credits consumed over time — plotted as the difference between polls, not the cumulative curve (which says nothing useful over a sliding window). Both figures appear in the chart's table view.
  • By action type — where credits went: Triage, Remediation, Fusion, DAST correlation, Auto Triage.
  • Top consumers per level (user, project, group, application), with any configured limit marked so you see headroom next to consumption.
◆
The unmatched-usage banner

If the dashboard warns that some consumption "could not be matched to a Checkmarx user," those credits count towards nobody's limit. Follow the link to resolve it.

06 — Daily use

Setting limits

A limit is a credit budget on one entity, for one period. Create and manage them on the Limits page — one tab per level (user, group, project, application), each with a live usage bar.

SettingWhat it does
Credit limitThe budget for the period.
Warning thresholdPercentage at which the entity is flagged as "near a limit" and a notification is raised — before anything is restricted.
PeriodLifetime, custom range, monthly or quarterly. The period type decides how history is counted — see below.
Monitor / EnforceMonitor only warns. Enforce restricts access when breached. New limits default to monitor.
ExemptionsAn entity on the exemption list is evaluated but never restricted — for break-glass accounts and projects that must never lose AI features.
Bulk edit & CSVChange many limits at once, or import/export the whole set as CSV.
◆
The most restrictive limit wins.

A user can be restricted by a group, project or application limit they never saw. When investigating, remember that overlapping limits all apply and the tightest one fires.

07 — Daily use

How usage is measured

This is the one idea worth understanding. Checkmarx's consumption endpoint returns aggregate totals over a lookback window — not a stream of timestamped events. There are no event IDs or timestamps, so per-period usage cannot be summed from events. Instead:

  1. Each cycle stores the reported totals (a snapshot).
  2. When a budget period opens, the total reported at that moment becomes the period's baseline.
  3. Usage for the period is latest reported total − baseline.

The baseline depends on the period type, because the period type is what decides whether history should count:

PeriodBaselineWhy
LifetimeZero — everything counts"Lifetime" means all credits ever. Discounting history would silently redefine it.
Custom rangeZero — everything countsYou chose the window explicitly and expect consumption inside it to count.
Monthly / quarterlyTotal when the period openedThe lookback window is wider than the period, and the API does not say when credits were spent — so counting the lot would let a year of history exhaust a fresh monthly budget on day one. Set count_existing_usage to include it anyway.
◆
Why a number can read as 0 of 10 when Checkmarx says 13

The 13 was spent before the period opened, so it sits in the baseline. The Limits page shows both the reported total and the discounted amount under the bar, so this is always explained rather than mysterious.

08 — Daily use

Attribution & disputes

The consumption feed identifies users inconsistently: some rows carry a clean email, some a display name, some a service-style handle like cx-ryan-wakeham. Attribution runs in two stages so credits reach the right person's budget.

Stage 1 — exact match

Email, then an email found in the name field, then username, then unambiguous full name. Two different people with the same name are never merged into one budget.

Stage 2 — similarity, for the messy tail

A handle the exact ladder can't place is normalised to a token set — the cx- prefix stripped, an email reduced to its local part — so cx-ryan-wakeham, Ryan Wakeham and ryan.wakeham@checkmarx.com all reduce to {ryan, wakeham} and score against every synced user. The score, kept deliberately conservative because a wrong match bills the wrong person, decides the outcome:

ConfidenceOutcome
≥ 85% one clear winnerMatched automatically and written to the audit log. Counted from the next poll — and still overridable.
≥ 60% or a near-tieLeft uncounted and raised as a dispute with ranked suggestions to confirm.
below 60%Unmatched — map it by hand. Automation handles like dependabot[bot] are flagged and kept out of the queue.

The attribution queue

On Settings → Consumption attribution, subjects are grouped into three tabs:

Disputes

A likely user was found but not with certainty. Click a suggestion chip to confirm, or map to any user. Nothing counts until you do.

Auto-matched

Matched automatically at high confidence and counted. Review, and override any that look wrong.

Unmatched

No user resembled the handle. Map by hand. Bots appear here and are never counted.

A manual mapping always wins over the automatic decision, and takes effect from the next poll onward.

09 — Daily use

Enforcement

When an enforcing limit is breached, CxCreditGuard turns off the AI features that spend credits for that entity. What changes depends on the level:

Level breachedWhat changes
UserThe AI roles and the scan-viewing role are unmapped from the user on the ast-app client.
ProjectAuto Triage is disabled, and PR triage & remediation is disabled by clearing the remediation severities.
GroupBoth project actions, on every project in the group.
ApplicationBoth project actions, on every project in the application.
↺
Everything is reversible.

Before any change, the exact prior state is snapshotted onto the enforcement record — which roles the user held, the project's Auto Triage config, the prior severity list. Restore access replays that snapshot. A feature that was already off beforehand stays off on restore.

10 — Daily use

Notifications

The Notification Center is always the record of truth — a filterable feed with an unread badge, an active-restrictions table, and one-click Restore access. Email and webhook are optional copies, so a broken SMTP server can never lose a warning.

  • Minimum severity filters what gets pushed out (default: warning and above), so quiet informational events don't wake anyone.
  • Retries stop after three failed delivery attempts, so a dead endpoint isn't retried forever. Changing the delivery settings resets the counters.
  • Signed webhooks — when a signing secret is set, each request carries an HMAC-SHA256 signature over a timestamped body, so a captured request can't be replayed.

Both channels are configured on Settings, which has a Send a test button that delivers a sample without leaving a row in the feed.

13 — Operating it

Security posture

A condensed view; the repository README carries the full detail and threat model.

  • Secrets at rest — API key, TOTP and delivery secrets are encrypted with AES-256-GCM, with per-purpose keys derived from the master key. The master key comes from the environment or a mounted file and is never stored in the database.
  • Utility auth — Argon2id password hashing, an enforced policy, optional TOTP, opaque session tokens stored only as digests, HttpOnly/Secure/SameSite=Strict cookies, idle and absolute timeouts.
  • Abuse resistance — per-username and per-IP rate limiting with account lockout; identical timing and messaging for unknown users and wrong passwords.
  • Transport & app — HTTPS with HSTS, a strict CSP with no inline scripts, CSRF double-submit, RBAC, ORM-only parameterised SQL, and an append-only audit log.
  • Container — non-root user, dropped capabilities, no-new-privileges, and no compiler or package manager in the final image.

14 — Operating it

Runbooks

Turning enforcement on for the first time

The failure mode of this tool is restricting the wrong person, so go slowly:

  1. Connect with a read-only key; leave every limit on monitor.
  2. Let it run for at least one full budget period. Are the figures what you expect? Is anyone showing as disputed or unmatched?
  3. Fix attribution first — an unmatched user is a budget that silently undercounts.
  4. Add exemptions for break-glass accounts and must-never-restrict projects.
  5. Switch one limit to enforce, on an entity you control, and verify both the restriction and the restore end to end.
  6. Only then widen, using bulk edit.

The tool restricted someone it should not have

  1. Restore first, investigate second. Use Restore access in the Notification Center — it replays the exact captured state. Don't hand-edit roles in Checkmarx, or the undo snapshot goes stale.
  2. Stop the re-fire. Switch that limit to monitor or add the entity to exemptions, otherwise the next cycle re-enforces.
  3. Find the cause. The Audit Log holds before/after state for every action, and the raw consumption payload is stored on each event for exactly this comparison.

A figure on screen doesn't match Checkmarx

Two causes look identical from outside; the built-in diagnostic separates them:

cd backend
python -m scripts.diagnose_usage --user "someone@example.com"
  • Attribution failure — credits were reported under a name that didn't match the synced user, so they count towards nothing. Fix it in the attribution queue.
  • Baseline effect — the credits matched but were spent before the period opened, so they sit in the baseline. Expected behaviour (see measurement).

15 — Operating it

Troubleshooting

I didn't see the admin password

On a reused volume the password is only printed the first time it's generated. Read it back from the container:

podman exec cxcreditguard cat /app/data/.admin_password

The container won't start (easy-entrypoint.sh: No such file or directory)

This is a line-endings problem from a Windows checkout rewriting the entrypoint script to CRLF. The repository pins these scripts to LF and the image strips carriage returns during build, so a plain rebuild fixes it. To also clean your working copy:

git config core.autocrlf false
git add --renormalize .
git checkout .

An IAM sync only read some of my users

User pagination is handled automatically. If a sync still reports fewer users than the tenant has, it warns with the exact shortfall rather than treating the partial list as complete — check the cycle warnings on the Dashboard.

A whole dimension shows as unavailable

Checkmarx silently returns the user view for a dimension a tenant doesn't support. CxCreditGuard detects this and marks the dimension unavailable rather than filing one entity's usage as another's. Limits at that level simply aren't evaluated — nothing is assumed to be zero.

◆
When in doubt, run a cycle and read the warnings.

The cycle result names every step's outcome — users synced, records ingested per dimension, limits evaluated, warnings raised, restrictions applied, and any step that failed.
