Governance for Checkmarx One AI credits

Budget, watch, and cap AI credit spend — safely.

Checkmarx One spends AI credits on Triage, Remediation, DAST correlation, Fusion scans and Auto Triage, but gives you no way to budget them per user, group, project or application. CxCreditGuard polls consumption on a schedule, compares it against limits you define, and can restrict access when a budget is breached — with every restriction recorded and reversible in one click.

This guide walks an administrator from first deploy to running enforcement in production. If you only read one thing, read How usage is measured — it explains the single non-obvious idea the whole tool is built on.

01 — Start here

What CxCreditGuard is

It is a self-hosted governance layer that sits beside Checkmarx One. It never spends credits itself; it observes what Checkmarx reports and, when you ask it to, turns off the AI features that spend them. Three ideas shape everything:

Poll, don't stream

Checkmarx reports running totals over a lookback window, not individual events — so per-period usage is derived by comparison, not by summing events.

Attribute, don't guess

Every usage row is matched to a real user — exactly where possible, by similarity where not — and anything uncertain is surfaced for review instead of billed to the wrong person.

Act reversibly

Before any restriction, the prior state is snapshotted. Every enforcement is one click to undo, and a feature that was already off stays off on restore.

◆
Monitor first.

Every new limit defaults to monitor-only. Nothing is ever restricted until you deliberately switch a limit to enforce — so you can watch the numbers for a full budget period before anything acts.

02 — Start here

Features and limitations

What CxCreditGuard does today, and what it cannot do (or has not been verified to do) yet, with what each limitation means for you. The same list is on the app's About page (Settings → About, or About in the user menu) and in the README.

What it does

Measure and attribute

  • Reads AI credit use from Checkmarx One on a schedule (every 15 minutes by default) for every user, group, project and application.
  • Counts each billed action from Checkmarx One's credit activity log in the period it happened in, against its project and application by id and its person by email or username (the default usage source). Identical actions in the same second are each counted, never merged.
  • Falls back to the consumption summary (totals matched by name) while the activity log cannot be read, and never counts the same usage from both. Settings → Schedule & data can use the summary only.
  • Once a day, checks that the activity log adds up to the summary's total over the same 30 days, and shows a mismatch in Diagnose.
  • Integration accounts (bots, Auto-triage, Auto-remediation, accounts you list) count towards their project's budgets, and towards a person's budget only when their project had no active project budget at the time: never towards two user budgets.
  • Matches each usage row to a Checkmarx user: exactly where it can, by name similarity where not. Unsure matches wait for an admin to confirm.
  • Shows the usage that counts towards no budget, and why: automation (Auto Triage, bots, integrations without an email), people it could not match, and project or application names that match no project (an admin can map them).
  • Can also charge a project's Auto Triage credits to the person whose scan set it off (off by default).
  • Overview of spend over time, by action type and by top consumers, with each budget marked.
  • Explains a figure: each budget shows what Checkmarx reported and what the period's starting point discounted.

Budgets and requests

  • Budgets per user, group, project or application: monthly, quarterly, a custom range or lifetime.
  • A warning when usage reaches a set share of the budget (80% by default).
  • Every new budget only monitors until you switch it to enforce.
  • Exemptions, permanent or until a date, for people and projects that must never be restricted.
  • Bulk edit, and import and export as CSV.
  • Credit requests: when an admin allows it, viewers ask for more budget; an admin approves in full or in part, optionally until a date, or refuses with a reason.
  • Optional automatic approval of small increases, up to a cap you set (off by default).
  • Reports: where each budget is heading this period, chargeback by business unit (with a cost per credit if you set one), and a weekly summary by email (off by default).

Enforcement and safety

  • At the limit, an enforcing budget removes a person's AI roles, or turns off Auto Triage, PR triage and remediation and Fusion (your choice) on the projects it covers.
  • Records what was there before every change; Restore access puts it back in one click.
  • Gives access back by itself when usage drops under budget, the budget is raised or a new period starts (unless the budget is set to hold until released).
  • Simulation: a dry run of the next cycle showing who would be warned and restricted, before anything happens.
  • Enforcement coverage: how many of the people holding an AI role a user restriction could actually take it from, and why not the rest (composite roles, groups, protected roles), with a warning when user budgets will not bite. It never changes the role list.
  • Safety ceilings: a cycle about to restrict more than 25 budgets or 100 users and projects restricts nobody and pauses itself.
  • A pause switch stops new restrictions at once; warnings and giving access back carry on.
  • Protected roles (ast-admin and iam-admin by default) are never restricted.
  • A sudden fall in reported usage is held, not believed, until later readings confirm it.

Watch and alert

  • Reads each restriction back and puts it back if someone undid it in Checkmarx One.
  • Policy violations (admins only): settings switched back on, Fusion scans during a restriction, usage still rising after one.
  • A Notification Center, with copies by email and webhook (optionally signed), filtered by severity.
  • Checks the API key's permissions and says what is missing before it matters.
  • An audit log of every action and change, chained so that an edited or deleted entry can be detected.

Operate

  • Runs on your own server: one container with SQLite, or Compose with PostgreSQL behind an HTTPS proxy.
  • Admin and viewer accounts, two-factor sign-in with recovery codes, password reset by email.
  • In-app updates for the single container: signed releases, installed in a quiet hour, rolled back if the new version does not start.
  • Configuration backup (settings, budgets, exemptions) to download, email or restore. Compose also dumps the database daily.
  • Demo mode with made-up data that never touches a tenant.
  • Two looks, Standard and Command Center, each in light and dark.
◆
What it connects to.

Your Checkmarx One tenant; your mail server and your webhook, only if you set them up; and, only with a registry token entered under Settings → Updates, GitHub's container registry (ghcr.io and pkg-containers.githubusercontent.com) to check for and download releases. No telemetry, no analytics, and nothing else is contacted.

Limitations

LimitationWhat it means for you
It acts once a cycle, not the moment credits are spent.Usage is read and budgets judged once a cycle (every 15 minutes by default), and Checkmarx can report credits a little after they are spent. Usage in between can take a budget past its limit before the restriction lands, so leave some headroom. A large group or application is restricted over several cycles (at most 1,000 changes a cycle by default).
It restricts access, it does not meter credits.It removes roles and turns settings off; it cannot stop an action already running or cap a budget to the exact credit.
Only roles held directly are removed.An AI role a person holds through a group or a composite role stays in effect. CreditGuard says so once and never changes the group or role, because that would affect everyone in it. Remove it there in Checkmarx One, or exempt the person (see Enforcement).
User budgets may not bite at all.On a live tenant ast-admin, held by 274 of 296 users, is a composite role containing all three default AI roles, and it is protected: a user restriction would have reached almost nobody. Check Enforcement coverage (Simulation or Settings → Enforcement) before relying on user budgets; project, group and application budgets still turn AI features off on projects.
A project budget does not stop people's own AI Triage and AI Remediation.Turning project features off leaves what people start themselves working; only a user budget stops that.
Account-wide Auto Triage may override a project.If Auto Triage is switched on for the whole account and projects cannot override it, turning it off on one project does not hold. CreditGuard notices on the second read-back and says so once: turn it off in the account's Auto Triage settings, or exempt the project.
Turning Fusion off is not airtight.A scan started with its own settings may still run Fusion; the lock against that is not verified. The AI engine can still run without Fusion, and whether that costs credits is not known. Such scans are recorded as policy violations.
The general Risk Management roles are used for now.AI Triage and AI Remediation are reached through them today, so a restricted person also loses the Risk Management pages and dashboard. When Checkmarx One's dedicated AI permissions reach your tenant, swap them in under Settings → Enforcement, Roles a user restriction removes.
A cycle or two of usage is not counted when the usage source switches.When the activity log becomes the source (the setting turned on, or the log back after failing), its first read only records what it holds: what happened since the summary's last reading is not counted. When the summary takes over (the setting turned off, the log refused or malformed, or failing for more than an hour), its first reading counts nothing: about one to two cycles are not counted. While the log fails for less than an hour nothing new is counted; it is counted when the log answers again. A row reaching the log more than about two hours late is counted only by the daily full read, and only if dated after the switch; rows of the same second that meet at a page boundary wait for a later cycle (see The credit activity log).
Figures only cover Checkmarx's lookback window.The consumption summary reports totals over a window (at most the last year), and the activity log covers the last 30 days. "Lifetime", custom and count-existing budgets read the summary's totals, so they mean everything in that window. Monthly and quarterly budgets do not count credits spent before the period opened (or before the budget was created), unless the budget is set to (see How usage is measured).
Unmatched usage counts against nobody.Credits reported under a name that matches no Checkmarx user, or an unconfirmed match, count towards no person's budget until an admin maps them (see Attribution); a mapping counts from then on. Automation counts towards a person only by the integration-account rule (Auto-remediation towards nobody: no scan initiator is traced for it). With the summary as the source, project usage reported under a repository name that is no project counts towards no project, group or application budget until mapped; the activity log names projects by id. All of it is shown on the Overview.
Credits per action are measured, not quoted.Checkmarx's listed rate is not what a Fusion or DAST correlation action costs (on a live tenant about 109 credits per Opus 5.5 Fusion scan against a rate of 2). Where they disagree, messages price an action at the feed's average over the lookback window and say so; it is an average, not the cost of one scan.
It cannot say who undid a restriction.Checkmarx One does not report who switched a setting back on. By default each restriction is read back once an hour, so a setting switched back on can stay on for up to about that long, and one undone and redone between two read-backs is not seen.
Some Checkmarx behaviour is not yet verified on a real tenant.Where a person's roles come from (groups, composite roles); the Fusion lock and the repository's Fusion setting; usage rows per group (only ever seen empty; the sum of its projects is used instead); writes of PR triage and remediation and Auto Triage in the shape a live tenant reads them (sent back as read, not yet tested by a write on one); finding a project's repository (without it, PR triage and remediation is skipped there); whether a Fusion setting the project inherited can inherit again after Restore (for now it is restored on the project itself). Each degrades safely and says so rather than guessing.
Tested to 2,000 projects on a synthetic tenant.Load tested with 2,000 projects and 1,000 users made up for the test, not on a real tenant of that size. Use PostgreSQL above about 500 projects or 300 users.
One instance only.A second copy against the same database refuses to start. Availability comes from restarting the one copy, not from running several.
The database is the only record of how to undo a restriction.The in-app backup holds configuration only. Back the database up; after restoring an older one, restrictions made since it was taken have to be given back by hand in Checkmarx One.
Updates are only as trustworthy as the release signing key.Until the image carries the release signing key, auto-update installs nothing and a manual install cannot be verified. Updates need a registry token, and only the single container updates itself: Compose shows the steps instead. Operating system, Python and OpenSSL fixes need a new image.
The audit log is tamper-evident, not tamper-proof.An edited or deleted entry is detected, but someone with full write access to the database could rewrite the whole chain.

03 — Start here

How it works

CxCreditGuard is one deployable unit: a backend that also serves the web UI from the same origin, a background scheduler in the same process, and a database (SQLite by default, PostgreSQL for the hardened deployment). Everything of consequence happens in one loop — a cycle — run on a schedule or on demand.

🔄 Sync
org_sync
Users, groups, projects, applications
→
📥 Ingest
ingestion
Poll consumption, snapshot, attribute to users
→
⚖️ Evaluate
evaluation
Usage vs limits, using period baselines
→
🛡️ Enforce
enforcement
Reversible role & AI-feature changes
Each step writes to the database and raises notifications; the web UI and email/webhook read from there.

You can run a cycle by hand any time from the Dashboard or Settings (Run a cycle now), which is the fastest way to see a change take effect without waiting for the schedule.

04 — Start here

Deploy

Two supported paths, both on Podman. Start with the single container to try it; use Compose to run it for real.

Quick start — single container

The whole tool ships in one image (UI bundled with the API) over plain HTTP on port 8000, with no required configuration: on first start it generates its own encryption key and a first admin account. From the repository root: 

# Linux / macOS / WSL
make podman-run

# Windows: run.bat (cmd.exe)  or  .\run-podman.ps1 (PowerShell)

Each builds the image, starts the container, and tails the startup log — which prints the initial admin credentials on a fresh volume. Then open http://localhost:8000.

▲
This convenience image runs over plain HTTP

Secure cookies are disabled because a browser silently discards them over HTTP. It is perfect for a local look, but do not expose it directly to the internet — use the Compose path for that.

Hardened deployment — Podman Compose

For production (HTTPS via an nginx TLS proxy, plus PostgreSQL), run the root docker-compose.yml with Podman Compose (Podman 4.1+):

cp .env.example .env
# Generate a master key for the .env file:
python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"

Set CXCG_MASTER_KEY (the value printed above — everything encrypted at rest depends on it) and POSTGRES_PASSWORD. To create the first admin, also set CXCG_BOOTSTRAP_ADMIN_USERNAME and CXCG_BOOTSTRAP_ADMIN_PASSWORD before the first start, then remove them after logging in. Provide a TLS certificate per deploy/nginx/README.md, then: 

podman compose -f docker-compose.yml up -d
podman compose -f docker-compose.yml logs -f app
⚠
Back up the data volume

The master key lives in cxcreditguard-data (single container) or your database plus CXCG_MASTER_KEY (Compose). Lose the key and stored Checkmarx secrets become unrecoverable.

05 — Start here

First-time setup

  1. Sign in and change the password. Use the credentials from the startup log (single container) or the ones you set in .env (Compose). You will be asked to change the password on first login.
  2. Connect Checkmarx. On the Setup page, paste an API key. The tool derives the tenant and region and shows them for you to confirm before anything is stored, then tests the connection. You can override the regional base URL if needed.
  3. Let a cycle run. Either wait for the schedule or press Run a cycle now. The first cycle syncs your organisation model and takes the first usage snapshot.
  4. Review attribution. Open Settings → Consumption attribution and clear any disputes so usage counts against the right people (see Attribution).
  5. Add limits in monitor mode and watch for a full period before enforcing (see Runbooks).
◆
Use a dedicated service account

Not a person's key. A named engineer's key inherits their permissions, breaks when they leave, and makes the audit trail read as though they personally restricted every colleague. A read-only key runs the whole tool in monitor-only mode.

06 — Daily use

The dashboard

The dashboard answers "what is being spent, by whom, and is anything at risk" at a glance.

  • Status tiles — credits reported for the window, entities near a limit, entities restricted, and the next scheduled run.
  • Credits consumed over time — plotted as the difference between polls, not the cumulative curve (which says nothing useful over a sliding window). Both figures appear in the chart's table view.
  • By action type — where credits went: Triage, Remediation, Fusion, DAST correlation, Auto Triage.
  • Top consumers per level (user, project, group, application), with any configured limit marked so you see headroom next to consumption.
◆
The unmatched-usage banner

If the dashboard warns that some consumption "could not be matched to a Checkmarx user," those credits count towards nobody's limit. Follow the link to resolve it.

08 — Daily use

How usage is measured

There are two sources. By default the credit activity log — one row per billed action, with its date and its project's id — feeds the budgets of projects, users and applications (see below). The consumption summary is still read every cycle: it feeds everything else (a group's own row; lifetime, custom and “count existing usage” budgets read its totals), the dashboard and Attribution, and takes over whenever the log cannot be read. Usage source: Summary only (Settings → Schedule & data) makes it the only source, exactly as before.

This is the one idea worth understanding about the summary. Checkmarx's consumption endpoint returns aggregate totals over a lookback window — not a stream of timestamped events. There are no event IDs or timestamps, so per-period usage cannot be summed from events. Instead:

  1. Each cycle stores the reported totals (a snapshot).
  2. When a budget period opens, the total reported at that moment becomes the period's baseline.
  3. Usage for the period is latest reported total − baseline.

The baseline depends on the period type, because the period type is what decides whether history should count:

PeriodBaselineWhy
LifetimeZero — everything counts"Lifetime" means all credits ever. Discounting history would silently redefine it.
Custom rangeZero — everything countsYou chose the window explicitly and expect consumption inside it to count.
Monthly / quarterlyTotal when the period openedThe lookback window is wider than the period, and the API does not say when credits were spent — so counting the lot would let a year of history exhaust a fresh monthly budget on day one. Set count_existing_usage to include it anyway.
◆
Why a number can read as 0 of 10 when Checkmarx says 13

The 13 was spent before the period opened, so it sits in the baseline. The Limits page shows both the reported total and the discounted amount under the bar, so this is always explained rather than mysterious.

The credit activity log (the default)

Each cycle reads the log first and counts every new event in the month and quarter of the event's own date, towards each active budget created before it happened: its project's (by id, no name matching), the project's groups' (not a plain group budget its own summary row feeds), its application's (the row's application id and the project's synced applications, once), and its person's: the IAM user by email, else by username (with your mappings and the usual matching ladder), else nobody, with the name raised under Settings → Attribution. Each budget counts an event once — a group budget that includes member usage too.

Identical rows are distinct events. The log has no row id, and two triage actions in the same second look exactly alike, so nothing is ever deduplicated. Instead CreditGuard keeps, for each identity (every field of a row), how many such rows it has seen; a read holding more than that counts the difference, in the same transaction that feeds the budgets. Nothing is written while Checkmarx is being called.

No row is ever read twice. Pages are read oldest first (sort_order=asc): new rows arrive at the end and old ones leave from the front, which can make a row near a page boundary be skipped (counted in the next cycle) but never read twice. Where the same second appears on both sides of a page boundary, that second's rows wait for a later cycle; where the order goes back, nothing of that read is counted. So the count can lag, never exceed. A normal cycle reads only the last two hours or so (two or three requests even at 100,000 rows a month); at most Activity log pages per cycle (40) are read, and a cycle that stops early counts only complete data and says so. Once a day the whole 30 days are read, late rows are counted, and the sum is compared with the summary's total: Diagnose shows Usage source with a warning on a mismatch.

Switching source never counts usage twice. When the log becomes the source (the setting turned on, the first cycle after upgrading, or the log back after failing), its first read only records what it holds, and nothing dated before that is ever counted from it; the summary stops feeding those budgets in the same cycle. When the summary takes over (the setting turned off; the log answering 403, 404 or nonsense; or failing for more than an hour), its first reading counts nothing. Either way about one to two cycles of usage are not counted. A shorter outage keeps the log as the source: nothing new is counted meanwhile, and what happened is counted when it answers.

Integration accounts

Bots and automation — [bot] accounts, Auto-triage, Auto-remediation, handles that name an integration, and the names you list under Settings → Attribution → Integration accounts — always count towards their project's budgets and the project's groups and application. Towards a person: if the project had an active project budget when it happened, towards no user budget. Otherwise Auto-triage goes to the person who started the scan (with auto-triage charging on; nobody otherwise; the same rule applies to those charges), Auto-remediation to nobody, and any other account to the person you map it to, or to a user budget set on the account itself (the Budgets picker offers it as name (integration account); it is monitor only). A project budget created mid-period applies from then on. One event is never charged to two user budgets.

09 — Daily use

Attribution & disputes

The consumption feed identifies users inconsistently: some rows carry a clean email, some a display name, some a service-style handle like cx-dave-dawson. Attribution runs in two stages so credits reach the right person's budget.

Stage 1 — exact match

Email, then an email found in the name field, then username, then unambiguous full name. Two different people with the same name are never merged into one budget.

Stage 2 — similarity, for the messy tail

A handle the exact ladder can't place is normalised to a token set — the cx- prefix stripped, an email reduced to its local part — so cx-dave-dawson, Dave Dawson and dave.dawson@example.com all reduce to {dave, dawson} and score against every synced user. The score, kept deliberately conservative because a wrong match bills the wrong person, decides the outcome:

ConfidenceOutcome
≥ 85% one clear winnerMatched automatically and written to the audit log. Counted from the next poll — and still overridable.
≥ 60% or a near-tieLeft uncounted and raised as a dispute with ranked suggestions to confirm. One that already counted towards a user keeps counting there until you resolve it.
below 60%Unmatched — map it by hand. Automation (handles with [bot], and integration identities: no email, matching nobody, and a handle with a CI, SCM or build part such as -bot, -ci, svc-, GitHub-Actions or sonar-scanner, or a lowercase build name such as jenkins or buildserver01) stays listed in the Unmatched tab, marked Automation and mappable, but is not chased as a person: one "new automation identity" notice, once per subject, instead of a "could not be matched" one. Digits, hyphens or underscores alone never make a person automation (jsmith2, Jean-Luc, mary_ann and Jenkins stay people).

The attribution queue

On Settings → Consumption attribution, subjects are grouped into three tabs:

Disputes

A likely user was found but not with certainty. Click a suggestion chip to confirm, or map to any user. Nothing counts until you do.

Auto-matched

Matched automatically at high confidence and counted. Review, and override any that look wrong.

Unmatched

No user resembled the handle. Map by hand. Automation is listed here too, marked Automation; it counts towards no user limit until you map it to a person. Project and application names that match no project are mapped in their own card below. Monthly and quarterly budgets count the increases CreditGuard sees between one reading and the next, towards wherever the name counts at that moment. So a mapping counts forward only: usage reported under the name from now on counts towards the project you chose, and what it reported before is not counted towards anyone. Unmapping it, mapping it elsewhere or correcting an automatic match moves only its future usage: what it already counted towards a budget stays there; the confirmation says so. Lifetime, custom and “count existing usage” budgets count everything reported under the names that count towards them now, history included. A project or user created and used before the next sync keeps its first usage once the sync brings it, if its name matches it; a name you map counts only from then on. A project renamed in Checkmarx keeps counting under its new name, whichever of the sync or the consumption feed reports the rename first; usage reported between the two may be lost, never counted twice. A project deleted and restored, or a name missing from a reading, counts only what it reported since. Usage counts towards the month (or quarter) in which CreditGuard read it; if CreditGuard read no usage between the last reading of one period and the first of the next (downtime, demo mode, a skipped cycle), what was used in between counts towards neither. A sudden fall in one name while the feed looks incomplete is not believed until a complete reading confirms it, or for at most three readings or two hours; Diagnose lists any fall held this way. Switching a budget between monthly and quarterly, or to lifetime or “count existing usage” and back, keeps what was used meanwhile. A disputed match counts towards nobody until you resolve it; what it counted before stays.

A manual mapping always wins over the automatic decision, and takes effect at once on the latest reading, and counts what the subject reports from then on.

10 — Daily use

Enforcement

When an enforcing limit is breached, CxCreditGuard turns off the AI features that spend credits for that entity. What changes depends on the level:

Level breachedWhat changes
UserThe AI roles mapped to the user directly are unmapped on the ast-app client: the roles listed under Settings → Enforcement, Roles a user restriction removes (by default view-risk-management, view-risk-management-dashboard, view-risk-management-tab). Scan viewing is left as their Checkmarx permission has it.
ProjectWhat the limit's What to turn off for projects choice says: Auto Triage is disabled; PR triage & remediation is disabled by clearing the remediation severities; Fusion is turned off in the project's scan settings (and in its repository's settings where Checkmarx reports one).
GroupThe chosen project actions, on every project in the group.
ApplicationThe chosen project actions, on every project in the application.

What to turn off for projects. Each project, group and application limit has three checkboxes: Turn off Auto Triage, Turn off PR triage and remediation and Turn off Fusion. New limits start with all three. A limit made before the choice existed keeps turning off Auto Triage and PR triage and remediation only, until you change it. Taking an action off a limit that is restricting now puts that setting back straight away. The Simulation page and the blast radius in the limit form count what the choice would turn off.

Which roles a user loses. The default three roles are general Risk Management roles: AI Triage and AI Remediation are reached through them, so a restricted person also loses the Risk Management pages and dashboard. Settings → Enforcement, Roles a user restriction removes, lets an admin pick other roles from the tenant's own list. Checkmarx One is to ship dedicated AI Triage and Remediation roles on 10 January: when they are on your tenant, add them to the list and remove the general ones. A change applies only to restrictions made from then on; a restriction in force keeps, and gives back, exactly the roles it recorded. A protected role cannot be on the list, and a role that looks like an administration role (*admin*, manage-*, realm-*, iam-*) is marked and needs a confirmation.

Roles held through a group or a composite role. CreditGuard can only remove a role mapped to the person directly. Before restricting, it looks (best effort) at where each AI role comes from: the person's groups and parent groups, and composite roles that contain it. A role still held that way is not taken away, and CreditGuard says so once: <user> keeps <role> through group <name> / role <name>; CreditGuard removed only the direct mapping. Remove it from the group or role in Checkmarx One, or exempt the person. CreditGuard never changes groups or composite roles (that would affect everyone in them), and it does not count such a role as drift every cycle. If these reads are refused, the source is shown as unknown and the restriction goes ahead.

Settings are read back. After turning Auto Triage or PR triage and remediation off, CreditGuard reads the setting back. Still on once is retried quietly on the next cycle (the read may be behind). Still on the second time, it is said once and not sent again that period: for Auto Triage this means the project's Auto Triage is set account-wide ("select all") and the project cannot override it, so turn it off in the account's Auto Triage settings or exempt the project. What was there before is kept, so Restore stays exact.

Simulation shows, for each person who would be restricted, the roles they would lose (with what each grants), the roles they would keep and through which group or role, and, for projects, where turning Auto Triage off may not hold. It reads at most 50 people's roles per run and says when it stopped there, spends at most about 10 seconds reading, stops reading once Checkmarx One's IAM does not answer, and does not read again someone already restricted. Only admins see what a person holds; viewers see which roles a restriction would remove.

!
What turning Fusion off does not stop.

A scan started with its own settings can turn Fusion on for that one scan. CreditGuard also tries to lock the project's setting against that (Settings → Enforcement, Lock Fusion against per-scan override, on by default); whether Checkmarx One honours the lock is not verified, and a tenant that refuses the lock gets Fusion turned off without it. The AI engine can still run without Fusion (LLM-based scanning); whether that costs credits is not known. Turning Fusion off in a repository's settings is not verified either: it is skipped when Checkmarx does not report the setting, and a setting (or lock) that Checkmarx accepts but does not keep is noticed by reading it back on two consecutive checks (one read straight after a write can be behind it) and said once; a repository setting not kept is then not sent again that period. What was there before is always kept, so Restore puts it back. CreditGuard reads every restriction back (at least once an hour by default), re-applies it if it was undone, and records anything done against it under Policy violations.

↺
Everything is reversible.

Before any change, the exact prior state is snapshotted onto the enforcement record — which roles the user held, the project's Auto Triage config, the prior severity list. Restore access replays that snapshot. A feature that was already off beforehand stays off on restore.

11 — Daily use

Policy violations

CreditGuard does not rely on Checkmarx One keeping a restricted setting off: it reads each restriction back (each at least once an hour by default, spread over the cycles) and applies it again if it was undone. The Violations page (admins only; Policy violations in Jump to) is the record of what it found, so someone can follow it up:

What happenedWhat is recorded
Setting switched back onAuto Triage, PR triage and remediation, Fusion (or its lock), the repository's Fusion setting, or a user's AI roles found back on, and turned off again. Checkmarx One does not say who changed it. One record per restriction per budget period, counting how often it was found and when last.
Fusion scan during a restrictionA scan on a project whose Fusion is turned off, started after the restriction, that ran Fusion anyway: who started it, from where (web app, PR webhook), the branch, the model and, when the price is known, what it costs.

The AI-scan counts and scans not checked are Information: nothing to follow up, no notification, not counted on the top-bar light or the menu, and listed under the Information filter (the page opens on All violations). Each new violation raises one notification and lights a top-bar light and a count on the menu. A setting switched back on is notified in the Enforcement category, as a re-applied restriction always was: once per restriction per budget period for a user's roles, Auto Triage and PR triage and remediation, once a day for Fusion. Scans and usage are notified under Policy violations. Notifications and the audit log name the project, never the person: who started a scan is shown only here, to admins. Open one to see its evidence, add a note, and Acknowledge or Resolve it; both are audited.

12 — Daily use

Notifications

The Notification Center is always the record of truth — a filterable feed with an unread badge, an active-restrictions table, and one-click Restore access. Email and webhook are optional copies, so a broken SMTP server can never lose a warning.

  • Minimum severity filters what gets pushed out (default: warning and above), so quiet informational events don't wake anyone.
  • Retries stop after three failed delivery attempts, so a dead endpoint isn't retried forever. Changing the delivery settings resets the counters.
  • Signed webhooks — when a signing secret is set, each request carries an HMAC-SHA256 signature over a timestamped body, so a captured request can't be replayed.

Both channels are configured on Settings, which has a Send a test button that delivers a sample without leaving a row in the feed.

Enforcement fails with a clear 403 naming the missing permission rather than silently doing nothing. Projects the key cannot see are reported as a warning rather than undercounted quietly.

An admin's own key can still be refused. A Checkmarx One API key most likely carries only the roles chosen when it was created, not everything its owner holds, so a key made under a tenant administrator's account can lack permissions the administrator has in the browser. Use a dedicated service account with a key created for CreditGuard.

Key permissions check. CreditGuard checks the key with read-only calls when the connection is saved or tested, every few hours, and when an admin presses Check again (Settings → Connection → Key permissions). Changes (role mapping, Auto Triage, PR triage and remediation) cannot be tried without changing the tenant, so they show as not tested, or will fail when the matching read was refused; any 403 met at run time is added to the same report at once. A refused read is cleared by the next check that reads it successfully; a refused change is cleared only when CreditGuard next makes that same change successfully (Check again cannot test a change). While something needed with the current setup is confirmed missing, every page shows a banner, the top bar shows a Key permissions light, and admins get a pop-up once per sign-in explaining what is missing, what stops working, the roles the key has, and what to do. Gaps in things not in use (the credit pool, groups or applications while no such limit exists, enforce-mode calls while no limit enforces) and changes that are only probably refused are shown on the Key permissions card only.

Breach messages say what the period's credits went on (for example 4 of 3 credits used in November 2026: Fusion scan (Opus 5.5) 2 scans = 4 credits, priced from Checkmarx's credits per action when the period's counts can be trusted) and what the restriction does not stop: a limit that does not turn Fusion off says so, and removing a user's AI roles changes no project setting.

15 — Operating it

Security posture

A condensed view; the repository README carries the full detail and threat model.

  • Secrets at rest — API key, TOTP and delivery secrets are encrypted with AES-256-GCM, with per-purpose keys derived from the master key. The master key comes from the environment or a mounted file and is never stored in the database.
  • Utility auth — Argon2id password hashing, an enforced policy, optional TOTP, opaque session tokens stored only as digests, HttpOnly/Secure/SameSite=Strict cookies, idle and absolute timeouts.
  • Abuse resistance — per-username and per-IP rate limiting with account lockout; identical timing and messaging for unknown users and wrong passwords.
  • Transport & app — HTTPS with HSTS, a strict CSP with no inline scripts, CSRF double-submit, RBAC, ORM-only parameterised SQL, and an append-only audit log.
  • Container — non-root user, dropped capabilities, no-new-privileges, and no compiler or package manager in the final image.

16 — Operating it

Runbooks

Turning enforcement on for the first time

The failure mode of this tool is restricting the wrong person, so go slowly:

  1. Connect with a read-only key; leave every limit on monitor.
  2. Let it run for at least one full budget period. Are the figures what you expect? Is anyone showing as disputed or unmatched?
  3. Fix attribution first — an unmatched user is a budget that silently undercounts.
  4. Add exemptions for break-glass accounts and must-never-restrict projects.
  5. Switch one limit to enforce, on an entity you control, and verify both the restriction and the restore end to end.
  6. Only then widen, using bulk edit.

The tool restricted someone it should not have

  1. Restore first, investigate second. Use Restore access in the Notification Center — it replays the exact captured state. Don't hand-edit roles in Checkmarx, or the undo snapshot goes stale.
  2. Stop the re-fire. Switch that limit to monitor or add the entity to exemptions, otherwise the next cycle re-enforces.
  3. Find the cause. The Audit Log holds before/after state for every action, and the raw consumption payload is stored on each event for exactly this comparison.

A figure on screen doesn't match Checkmarx

Two causes look identical from outside; the built-in diagnostic separates them:

cd backend
python -m scripts.diagnose_usage --user "someone@example.com"
  • Attribution failure — credits were reported under a name that didn't match the synced user, so they count towards nothing. Fix it in the attribution queue.
  • Baseline effect — the credits matched but were spent before the period opened, so they sit in the baseline. Expected behaviour (see measurement).

17 — Operating it

Troubleshooting

I didn't see the admin password

On a reused volume the password is only printed the first time it's generated. Read it back from the container:

podman exec cxcreditguard cat /app/data/.admin_password

The container won't start (easy-entrypoint.sh: No such file or directory)

This is a line-endings problem from a Windows checkout rewriting the entrypoint script to CRLF. The repository pins these scripts to LF and the image strips carriage returns during build, so a plain rebuild fixes it. To also clean your working copy:

git config core.autocrlf false
git add --renormalize .
git checkout .

An IAM sync only read some of my users

User pagination is handled automatically. If a sync still reports fewer users than the tenant has, it warns with the exact shortfall rather than treating the partial list as complete — check the cycle warnings on the Dashboard.

A whole dimension shows as unavailable

Checkmarx silently returns the user view for a dimension a tenant doesn't support. CxCreditGuard detects this and marks the dimension unavailable rather than filing one entity's usage as another's. Limits at that level simply aren't evaluated — nothing is assumed to be zero.

◆
When in doubt, run a cycle and read the warnings.

The cycle result names every step's outcome — users synced, records ingested per dimension, limits evaluated, warnings raised, restrictions applied, and any step that failed.
